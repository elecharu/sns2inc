# [최우선] 기존 페이지 참조·공통 함수 활용 구현 및 정밀 검증 규칙

모든 화면·스크립트·프로시저 작업은 **현재 프로젝트의 다른 페이지가 이미 쓰고 있는 방식을 확인해서 그대로 구현**하고, **공통 함수·컴포넌트가 제공하는 기능을 먼저 찾아 사용**하며, **실제로 실행해 본 검증 결과로만 완료를 보고**합니다.
다른 규칙과 절차가 겹치면 이 규칙을 먼저 적용합니다. 단, `procedure.md` 0순위(실제 서버 DB 조작 금지)와 `common_component.md`(공통 컴포넌트 변경 금지)는 이 규칙보다 우선합니다.

---

### 1. 구현 전: 기존 페이지 방식 조사 의무
- **기능마다 같은 동작을 하는 기존 화면·프로시저를 검색해 호출 구조를 확인한 뒤 같은 형태로 작성합니다.** 가능하면 2곳 이상 비교하고, 결과 설명에 참고한 파일을 적습니다.
- 확인 예시 (실제 사례):

| 기능 | 확인할 것 | 참고 예 |
| :--- | :--- | :--- |
| 체크 행 삭제 | 확인창 먼저 → 콜백 안에서 `IsChecked` 행을 바로 `AddList` → `CallProc` | `EQM1002_R01.js`, `SAL1002_R04.js` |
| 스캔·Enter 입력 | 공통 Enter 처리(`MasterBase.js`: 안내창 Enter 확인, 다음 칸 이동)와 함께 동작하는지 | `PDA1200_R01.js`, `MasterBase.js` |
| 재고(COMLOT) 생성·차감·삭제 | 같은 테이블을 다루는 IO 프로시저의 생성·차감·삭제 조건 | `IO_ETC_IN`, `IO_ETC_OUT`, `IO_PRDRST_DELETE` |
| 테이블 관계 | 원본 프로시저가 실제로 INSERT하는 테이블과 키 | `IO_PRDRST` → `PRDRSTLOT`·`COMIN`·`COMINLOT`·`COMLOT` |

- **참고 소스가 원본 패턴인지 확인**: 최근 에이전트가 작성·수정한 화면은 기준으로 삼지 않고, 기존 개발자가 만든 화면의 방식을 기준으로 합니다. (`WORK_HISTORY.md`로 작성 이력 확인)
- **공통 프레임워크 동작은 소스를 직접 읽어 확인**합니다 (`MasterBase.js`, `ItsMsg.js`, `ItsText.js`, `ItsGrid.js`, `ItsMaria.js` 등). 이벤트 순서·포커스·기본값을 추측으로 정하지 않습니다.
- 요청에 없는 값·테이블·조건은 정하지 않고 `feature_spec.md`에 따라 `(확인 필요)`로 표시하거나 사용자에게 확인합니다.

### 2. 공통 함수·컴포넌트 우선 활용 (분석·작성 단계 필수 적용)
- **분석 단계**: 기능을 나누어 볼 때 각 동작마다 "공통 함수·컴포넌트로 되는가"를 먼저 확인하고, 결과 설명에 사용한 공통 기능을 적습니다. 공통 소스는 `UserControl/*.js`(화면), 공통 프로시저·함수(DB)를 직접 검색해 확인합니다 (`framework_convention.md` 1항).
- **작성 단계**: 공통 기능이 있으면 화면·프로시저에서 같은 동작을 직접 구현하지 않습니다. 공통 기능은 **사용만** 하고 수정하지 않습니다 (`common_component.md`).
- 자주 쓰는 공통 기능 (실제 프로젝트 사용 확인):

| 동작 | 공통 기능 | 직접 구현 금지 예 |
| :--- | :--- | :--- |
| 그리드 공통코드(COMTYPE) 명칭 표시 | `columnType: enumColumnTypes.combo, gpcd: '그룹코드'` + 프로시저는 코드만 반환 | 프로시저 `GPCD('ITEMTP', ...)`·COMTYPE JOIN으로 명칭 반환, 코드 hidden + 명칭 컬럼 (`framework_convention.md` 6항) |
| 메시지·확인창 | `ItsMsg.Alert`·`Confirm`·`Toast`, `ItsMsg.CommonMsg.SearchComplete`·`SaveComplete`·`DeleteComplete` | 같은 문구를 화면마다 직접 작성 |
| 날짜 기본값 | `ItsHelper.GetYearMonthDay`·`AddDay`, `ItsDateRange.SetInitValueFrom` | `new Date()`로 날짜 문자열 직접 조합 |
| 팝업·입력 초기화, 로그인 사원 | `ItsPage.InitData('패널ID')`, `ItsPage.EMPCD` | 컨트롤마다 빈 값 대입 반복, 사원코드 별도 조회 |
| 그리드 행 처리·체크 | `ItsGrid.AddRow`·`RemoveRow`·`IsChecked`, `isCheckBoxGrid: true` | store 배열 직접 조작, 체크 상태 별도 관리 |
| 키 발번·목록 분해·오류 | `GETKEY('키명')`, `COMSPLIT`, `COMERR` | MAX+1 발번, 문자열 직접 자르기, SELECT로 오류 문구 반환 |
| 감사·일시 | `CALLTIME()`·`CALLEMP()`·`CALLPRG()`, `GETTIME()`·`GETDATE()` | `NOW()`·세션 변수 직접 대입 (`procedure_audit.md`) |

- 공통코드(COMTYPE) 그룹은 콤보 컬럼을 쓰고, 거래처·사원 같은 마스터 테이블 명칭은 같은 메뉴 화면 형식(예: SAL 화면 `CUSTNM` 명칭 컬럼)을 따릅니다. 어느 쪽인지 COMTYPE `GPCD` 존재 여부와 기존 화면으로 확인합니다.

### 3. 중복 검증·잉여 코드 금지
- **프로시저가 확인하는 값(미선택, 필수값, 존재 여부, 수량)을 화면에서 다시 확인하지 않습니다.** 화면 확인은 프로시저가 알 수 없는 것(그리드에 모은 목록의 중복·입력 한도 등)에만 둡니다.
- 같은 목록을 배열에 모았다가 다시 넘기는 이중 반복, 이미 숫자인 값의 형변환, 화면에서 쓰지 않는 출력 컬럼·파라미터·변수를 남기지 않습니다.
- **요청하지 않은 디자인 변경(배경색, 버튼 색, 헤더·제목 추가 등)을 임의로 넣지 않습니다.** 요청한 배치·크기만 변경합니다.

### 4. SQL 정밀 검증
- JOIN마다 관계의 행 수(1:1 / 1:N)를 원본 프로시저·키로 확인하고, `DISTINCT`·`GROUP BY`·`LIMIT 1`로 중복 행을 숨기지 않습니다 (`sql_structure.md`).
- 같은 키로 여러 행이 생기는 데이터 경로(재작업 실적, 창고별 로트, 이동 입고 등)를 원본 프로시저에서 찾아 시나리오에 넣습니다.
- 여러 건을 한 번에 처리하면 같은 대상(같은 로트·창고 등)의 **합계 기준**으로 검증합니다.
- 저장·삭제는 **모든 확인을 먼저 끝낸 뒤 변경을 시작**합니다. 오류 시 롤백 여부를 소스로 확인할 수 없으면 일부만 반영될 수 있다고 보고 설계합니다.
- 기존 데이터(이미 있던 재고 행 등)와 이번 기능이 만든 데이터를 구분해 차감·삭제합니다.
- **읽는 값마다 실제로 쓰는 프로시저를 모든 경로에서 확인**합니다. 컬럼 이름만 보고 값이 채워진다고 가정하지 않고, 그 컬럼을 `INSERT`·`UPDATE`하는 프로시저를 검색해 경로별(웹 화면·현장 TML·PDA·국내/해외 출고·취소 등)로 언제 어떤 값이 들어가는지 확인합니다. 같은 정보가 여러 테이블에 있으면 모든 경로에서 항상 채워지는 원본을 사용합니다.
  - 사례 (SAL1004_R01): 생산실적 `PRDRST.ITEMCD`는 현장 실적(TML2020_R02 → PRDWORK 품목 없음)에서 빈 값 → 로트 품목 `COMLOT.ITEMCD` 사용
- **경로별 차이로 판단 기준(업무 의미)이 달라지면 바꾸기 전에 사용자에게 확인**합니다. 빈 값처럼 명백한 오류가 아니라 "어느 시점·상태를 기준으로 볼지"의 문제는 기획 결정입니다.
  - 사례 (SAL1004_R01): 출하지시 `SALOUT.OUTYN`은 해외 컨테이너 출고(IO_SALOUT_PDA)에서 마지막 컨테이너 후에만 'Y' → 실제 출고 이력 기준으로 임의 변경했다가, 기획 의도(출하완료 `OUTYN = 'Y'`만 반품 가능)에 따라 되돌림

### 5. 검증 실행 의무 (말로만 완료 금지)
- **로직은 실제로 실행해서 확인합니다.**
  - JS 로직: 모의 객체를 넣은 Node 테스트
  - SQL 로직: SQLite 등 격리 환경에서 기존·변경 쿼리를 같은 데이터로 비교
  - 키보드·안내창·포커스 동작: 실제 공통 스크립트(`jquery`, `ItsMsg.js`, `ItsText.js`, `MasterBase.js` 처리 원문)를 넣은 브라우저 테스트 페이지에서 키 입력
  - 화면 배치: 실제 컨트롤 템플릿·CSS로 만든 미리보기
- **검증 데이터는 원본 프로시저 흐름대로 만듭니다.** SQLite·모의 데이터의 행과 컬럼 값을 가정해서 채우지 않고, 4항에서 확인한 쓰는 프로시저의 `INSERT`·`UPDATE` 순서를 그대로 재현해 만듭니다 (빈 값으로 들어가는 컬럼은 빈 값 그대로). 가정한 값으로 만든 데이터는 가정이 틀린 경우를 통과시킵니다.
- **빈 값끼리 같다고 통과하는 비교를 확인합니다.** 같은 품목·같은 거래처 확인처럼 두 값을 비교하는 검사는 양쪽이 모두 빈 값·0인 케이스를 넣어, 검사가 실제로 막는지 확인합니다.
- 문제 수정은 **수정 전 문제를 먼저 재현**하고, 수정 후 같은 시나리오가 통과하는지 확인합니다.
- 정상·경계·예외·여러 건 동시 처리 케이스를 포함합니다 (`validation.md` 2항).
- 실행하지 못한 범위(MariaDB 컴파일, 실제 화면, 스캐너 등)는 결과 보고에 그대로 적습니다.
- 검증용 임시 파일·서버 설정은 끝난 뒤 삭제합니다.
