# SQL 구조 및 JOIN 최소화 규칙

프로시저·SQL 신규 작성, 수정, 최적화 시 반드시 적용합니다. 누구나 기준 테이블과 데이터 연결 흐름을 쉽게 이해할 수 있도록 짧고 직관적으로 작성합니다.

## 작성 전 확인
- 실제 컬럼·PK·인덱스·테이블 관계를 SELECT로 확인하고, 조회 결과 한 행이 무엇을 뜻하는지와 식별키를 먼저 정합니다.
- 필요한 출력값·조회 조건·정렬을 기준으로 최소 테이블을 선택합니다. 이미 가진 값이나 파라미터를 다시 얻기 위한 JOIN은 추가하지 않습니다.
- 각 값의 원본 테이블을 정하고, 같은 정보를 여러 테이블에서 반복해서 가져오지 않습니다.

## 누구나 읽기 쉬운 SQL
- 기준 테이블 하나에서 시작해 필요한 테이블만 식별키로 직접 연결합니다. 불필요하게 여러 테이블을 거쳐 값을 가져오지 않습니다.
- JOIN을 여러 번 이어 붙이거나 중첩 조회를 겹쳐 읽기 어렵게 만들지 않습니다. 같은 정보를 한 번의 연결로 얻을 수 있는 구조를 먼저 선택합니다.
- 테이블과 별칭은 역할을 바로 알 수 있게 짧고 명확하게 작성합니다. 의미 없는 번호 별칭과 장황한 이름을 피합니다.
- 연결키와 조건을 일관되게 배치해 FROM부터 WHERE까지 흐름을 따라 읽을 수 있게 합니다. 복잡한 SQL을 긴 주석으로 설명하는 대신 구조를 단순하게 만듭니다.

## 불필요한 JOIN 금지
- JOIN은 출력·필터·정렬·집계·관계 검증 등 필요한 용도가 있을 때만 사용합니다. 같은 키·조건·용도의 중복 JOIN은 제거합니다.
- SELECT에서 사용하지 않는다는 이유만으로 JOIN을 삭제하지 않습니다. INNER JOIN의 행 필터링과 LEFT JOIN의 행 증가 여부까지 확인합니다.
- 이미 연결한 테이블의 컬럼을 활용합니다. 동일 정보를 얻으려고 별칭만 바꾸어 재조인하지 않습니다.
- 확정된 그룹코드는 해당 컬럼에 직접 비교합니다. COMTYPE에 GPCD가 지정됐다는 이유만으로 JOIN이 불필요하다고 단정하지 않습니다.
- 예: $EQMGRP가 실제 FM116 그룹코드로 확인된 경우 다음 조건으로 필터링합니다.
  ```sql
  WHERE MSTEQM.EQMGUBUN = $EQMGRP
  ```
- 그룹명 표시·FM116 정렬순서·코드명 검색이 필요한 경우에만 COMTYPE을 참조합니다. 그룹명이 같아도 다른 그룹코드를 합치지 않습니다.
- JOIN을 줄이려고 행마다 실행되는 상관 서브쿼리나 함수를 늘리지 않습니다. 여러 행 SELECT의 WHERE EXISTS/NOT EXISTS 금지는 procedure.md를 따릅니다.
- DISTINCT, GROUP BY, LIMIT 1로 잘못된 JOIN의 중복 행을 숨기지 않습니다. 관계와 키를 먼저 바로잡습니다.
- JOIN 개수가 적거나 SQL이 짧다는 이유만으로 성능이 좋아졌다고 판단하지 않습니다.

## 테이블·컬럼 중복 방지
- HEADER의 식별정보는 연결키로 참조합니다. DETAIL에 PLANTP·PLANCD·REVNUM 같은 값을 불필요하게 반복 저장하지 않습니다.
- 새 테이블·뷰·임시 테이블은 기존 구조로 처리할 수 없는 목적이 확인된 경우에만 추가합니다. 단순히 SQL을 짧게 보이게 하려고 만들지 않습니다.
- 중복 컬럼 삭제 전 전체 참조 코드와 기존 데이터 연결·불일치를 확인하고, 로컬 전환 SQL과 영향받는 프로시저를 함께 준비합니다.
- CREATE TABLE IF NOT EXISTS는 기존 테이블을 변경하지 않습니다. 생성 SQL 수정과 실제 컬럼·PK·기본값 전환을 구분하며, 실제 DB 반영은 사용자가 진행합니다.

## 간결성 및 검증
- NULL 대체·형변환·문자열 가공은 실제로 필요한 위치에만 사용합니다. 기본값이 필요한 경우에만 IFNULL/COALESCE를 사용하고, 중첩하거나 반복하지 않습니다.
- 같은 파라미터 해석·코드 조회·집계를 반복하지 않습니다. 입력값 전처리는 한 번만 하고, 인덱스 컬럼을 불필요하게 함수로 감싸지 않습니다.
- 변경 전후 식별키·행수·중복·NULL·정렬·미등록 대상 및 영향받는 기능을 비교한 후 반영합니다.
- 성능 개선을 주장할 때는 SELECT EXPLAIN과 필요한 격리 환경 비교로 확인하고 근거를 작업 이력에 기록합니다. SQL 길이나 JOIN 개수만으로 최적화 완료를 선언하지 않습니다.
- 실제 서버 DDL/DML 실행 및 공통 컴포넌트 변경 금지를 유지합니다. 검증 절차는 validation.md, SQL 이력·주석은 procedure.md를 따릅니다.
