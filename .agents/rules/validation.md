# Function Validation Rule

모든 기능 개발, 리팩터링 및 버그 수정 작업 시 기존 기능의 훼손(회귀 버그)을 방지하고 코드 신뢰성을 확보하기 위해 다음 원칙을 반드시 준수합니다.

### 1. 선 검증 후 반영 (Verify First, Apply Later)
- 코드를 소스 파일에 즉시 반영하기 전에, 수정할 로직이 정상 동작하는지 테스트 스크립트나 콘솔 환경을 통해 **사전에 독립 검증**을 완료합니다.
- 검증 과정에서 문제가 발견되면 원인을 분석하고 보완한 뒤, 완전히 검증된 상태에서 소스 파일 수정을 진행합니다.

### 2. 다각도 테스트 케이스 고려
- 단순한 '정상 케이스'뿐만 아니라 발생 가능한 다양한 시나리오를 포괄하여 검증합니다:
  - **정상값 케이스**: 가장 일반적인 입력값에 대한 기대 동작 확인
  - **경계값 케이스**: 상한치/하한치 경계값, 최소/최대값, 0, 소수점 자릿수 등
  - **예외/엣지 케이스**: 빈 문자열(`""`), 미설정 기호(`"~"`), 공백, 잘못된 문자열, 소문자/대문자 차이 등
  - **화면 모드별 케이스**: 신규 등록 모드(`ADDBTN`), 기존 수정 모드(`UPBTN`), 자동 입력 버튼 동작 등

### 3. 컴파일 및 빌드 무결성 보장
- 소스 코드 파일(CS 등)을 수정한 후에는 반드시 **MSBuild 컴파일**을 실행하여 문법 오류나 참조 누락(Error 0건)이 없음을 확인합니다.
- 빌드 결과에 이상이 있을 경우 즉시 원인을 추적하여 해결하고, 항상 정상 빌드 상태를 유지합니다.

### 4. SQL 구조 변경 검증
- [SQL 구조 및 JOIN 최소화 규칙](sql_structure.md)에 따라 JOIN 목적과 원본 테이블을 확인한 후 변경합니다.
- 변경 전후 식별키·행수·중복·NULL·정렬 및 영향받는 기능을 비교합니다. JOIN이 조회 대상 제한에 쓰이는지도 확인합니다.
- 컬럼·키 변경 시 전체 참조 코드, 기존 데이터 연결, 전환 SQL 및 실제 DB 반영 상태를 구분하여 검증합니다.
- 성능 개선은 실행계획과 필요한 격리 환경 비교로 확인하고, 검증되지 않은 결과를 완료로 보고하지 않습니다.
