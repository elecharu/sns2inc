# Function Validation Rule

모든 기능 개발, 리팩터링 및 버그 수정 작업 시 기존 기능의 훼손(회귀 버그)을 방지하고 코드 신뢰성을 확보하기 위해 다음 원칙을 반드시 준수합니다.

### 1. 선 검증 후 반영 (Verify First, Apply Later)
- 코드를 소스 파일에 즉시 반영하기 전에, 수정할 로직이 정상 동작하는지 테스트 스크립트나 콘솔 환경을 통해 **사전에 독립 검증**을 완료합니다.
- 검증 과정에서 문제가 발견되면 원인을 분석하고 보완한 뒤, 완전히 검증된 상태에서 소스 파일 수정을 진행합니다.

### 2. 다각도 테스트 케이스 고려
- 단순한 '정상 케이스'뿐만 아니라 발생 가능한 다양한 시나리오를 포괄하여 검증합니다:
  - **정상값 케이스**: 가장 일반적인 입력값에 대한 기대 동작 확인
  - **경계값 케이스**: 상한치/하한치 경계값, 최소/최대값, 0, 소수점 자릿수 등
  - **예외/엣지 케이스**: 빈 문자열(`""`), 미설정 기호(`"~"`), 공백, 잘못된 문자열, 소문자/대문자 차이 등
  - **화면 모드별 케이스**: 신규 등록 모드(`ADDBTN`), 기존 수정 모드(`UPBTN`), 자동 입력 버튼 동작 등

### 3. 컴파일 및 빌드 무결성 보장
- 소스 코드 파일(CS 등)을 수정한 후에는 반드시 **MSBuild 컴파일**을 실행하여 문법 오류나 참조 누락(Error 0건)이 없음을 확인합니다.
- 빌드 결과에 이상이 있을 경우 즉시 원인을 추적하여 해결하고, 항상 정상 빌드 상태를 유지합니다.

### 4. SQL 구조 변경 검증
- [SQL 구조 및 JOIN 최소화 규칙](sql_structure.md)에 따라 JOIN 목적과 원본 테이블을 확인한 후 변경합니다.
- 변경 전후 식별키·행수·중복·NULL·정렬 및 영향받는 기능을 비교합니다. JOIN이 조회 대상 제한에 쓰이는지도 확인합니다.
- 컬럼·키 변경 시 전체 참조 코드, 기존 데이터 연결, 전환 SQL 및 실제 DB 반영 상태를 구분하여 검증합니다.
- 성능 개선은 실행계획과 필요한 격리 환경 비교로 확인하고, 검증되지 않은 결과를 완료로 보고하지 않습니다.

### 5. 사용 중단 컬럼 최종 검증
- **변경 범위 확정**: 컬럼별로 전체 사용 중단인지, 해당 화면의 저장에서만 제외하는지 먼저 구분합니다. 실제 DB 컬럼·기본값·NULL 허용 여부와 관련 화면·팝업·프로시저의 사용처를 SELECT 및 소스 검색으로 확인합니다. 읽기 전용 전환을 DB 컬럼 삭제로 판단하지 않습니다.
- **호출 경로 전체 추적**: 컬럼명·별칭·`_LIST` 파라미터·원본값 보관 변수를 함께 검색합니다. JS의 `AddList`·`AddParam`뿐 아니라 `AddPanel`·`AddRecord` 등 자동 수집 경로, 변경 비교·체크 처리·키보드·팝업 이벤트, 서버 입력부터 SQL 저장까지 확인합니다.
- **미사용 코드 완전 제거**: 확정된 중단 범위에서 전송 코드, 프로시저 입력·지역변수·목록 분해·검증·가공·INSERT·UPDATE 대입 및 더 이상 필요 없는 참조를 제거합니다. 주석 처리된 실행 코드도 남기지 않습니다. 조회나 별도 팝업에서 필요한 사용처는 유지하고 이유를 기록합니다.
- **숨은 의존 조건 확인**: 제외한 값이 NULL·빈 값으로 들어와 다른 컬럼을 초기화하거나 기존 값을 덮어쓰는 조건이 남아 있지 않은지 확인합니다. 저장 대상은 실제 필요한 식별코드와 입력값만 사용하고 표시명에 의존하지 않도록 정리합니다.
- **파라미터 일치 확인**: 프로시저 입력 변경 시 모든 호출부와 `SYSTEM_PARAMETERS` 등록 SQL을 함께 확인합니다. 제거·추가 후 이름·순서·개수·자료형이 일치하는지 검증하고, 등록 SQL의 설명과 적용 순서도 갱신합니다.
- **동작으로 최종 확인**: 실제 전송값 또는 독립 검증 환경에서 제외 컬럼이 저장 요청에 없는지 확인합니다. 기존 행 수정 시 해당 DB 값이 유지되는지, 신규 행이 기본값·NULL 제약에 맞게 저장되는지, 빈 값·삭제·여러 행 처리와 관련 팝업이 정상 동작하는지 검증합니다.
- **완료 전 재검색**: 수정 후 관련 JS·SQL·프로시저·호출부를 다시 검색하여 중단 범위의 활성 참조와 주석 처리된 잔여 코드가 없는지 확인합니다. 단순히 화면을 읽기 전용으로 만들거나 전송 한 줄을 주석 처리한 상태로 완료하지 않습니다.
- **검증 범위 명시**: 변경 파일과 제거한 항목, 계속 사용하는 예외, 테스트 결과를 기록합니다. 로컬 소스·격리 검증과 실제 서버 반영 여부를 구분하며, 실제 서버 변경은 `procedure.md`의 금지 원칙을 따릅니다.

### 6. 작업 완료 전 불필요한 잉여·쓰레기 코드 전수 점검 및 자체 삭제 의무화
- **자체 전수 검증 의무화 (사용자에게 검증 부담 전가 원천 금지)**:
  - 기능 구현이나 수정이 끝났다고 해서 곧바로 완료 처리하지 않고, 에이전트 스스로 수정한 모든 소스 파일(`.xaml`, `.cs`, `.js`, `.aspx`, `.sql`)을 전수 검사하여 미사용 변수, 잉여 파라미터, 주석 처리된 잔여 코드, 임시 우회 코드 등 쓰레기 코드가 100% 제거되었는지 독립적으로 검증합니다.
  - 사용자가 "이 코드 왜 있냐", "미사용 코드 지워라"라고 지적하기 전에 에이전트가 완벽히 정리하는 것을 기본 전제로 합니다.
  - 검증 대상: 미사용 컨트롤·바인딩, 비표준 임시 우회 로직, 미사용 DB 파라미터, 폐기된 주석 블록, 디버깅 잔여물 등.
