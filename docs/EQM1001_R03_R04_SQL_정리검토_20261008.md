**EQM1001_R03·R04 SQL 사용 여부 및 개선 검토 — 2026-10-08**

현재 저장소의 페이지 JavaScript·ASPX·C#과 S05A 보고서, SQL 참조를 확인했습니다. 실제 DB에서는 컬럼·키 및 중복 가능성만 SELECT로 확인했습니다. 서버 프로시저나 데이터는 변경하지 않았습니다.

**바로 삭제한 미사용 내용**

- R04 입력값 `CHKRSTKEY_LIST`, `EMPCD_LIST`, `PROBLEM_LIST`, `SOLUTION_LIST`: SQL 본문에서 읽지 않으며 현재 페이지에서도 전달하지 않는 과거 일괄처리 입력값입니다.
- R04 입력값 `CHKCYCLE_LIST`, 지역변수 `_$CHKCYCLE`, 해당 `COMSPLIT` 호출: 값을 분리한 뒤 INSERT·UPDATE·검증에서 사용하지 않습니다. 실적 상세에는 이 값의 저장 컬럼도 없습니다.
- R04 계획 조회의 `MSTEQMREV_DETAIL.CHKCYCLE` 반환값: 페이지에서 점검주기 리스트를 만드는 용도로만 전달하던 값입니다. 그 전달을 제거하고 반환값도 함께 정리했습니다. 승인본 테이블의 CHKCYCLE 컬럼은 삭제하지 않았습니다.
- R04 JavaScript 등록·수정 팝업의 `CHKCYCLE_LIST` 전달 2곳 및 SQL의 주석 처리된 DEBUG 설정을 삭제했습니다.
- R04 입력값은 22개에서 17개로 줄었습니다. 공통 호출 규격인 `CALLTYPE`, `KEYWORD`는 유지했습니다.

R03은 26개 분기 모두 사용되고, 지역변수도 모두 참조되어 삭제한 분기가 없습니다. R04의 6개 분기 역시 모두 사용되어 유지했습니다. R03 파일은 이번 작업에서 수정하지 않았습니다.

**표 1. 현재 구조의 문제 지점 — 개선 전**

아래 8건은 검토 후보입니다. JOIN·조회 조건·중복 검증의 코드는 이번 작업에서 삭제하거나 변경하지 않았습니다. JOIN이 길다는 이유로 전부 불필요하다고 판정하지 않았습니다.

| 번호 | 위치 | 현재 구조와 문제 지점 |
| --- | --- | --- |
| 1 | R03 / SAVE_PLAN_STATUS | 처음에 PLANCD가 NULL·빈 값인지 막은 뒤 다음 IF에서 같은 검사를 다시 합니다. 입력값 검증이 중복됩니다. |
| 2 | R03 / CALL_PLAN_RPT | PLANTP를 CASE로 G 또는 E로 정규화한 직후 `NOT IN ('G','E')`를 다시 검사합니다. 그 조건은 현재 흐름에서 항상 거짓입니다. |
| 3 | R03 / SAVE_PLAN_STATUS | 그룹의 최신 미승인 설비 REV를 찾는 MSTEQM·EQM_REV·NEXT_REV JOIN을 잠금 조회와 재요청 필요 검사에서 반복합니다. 첫 조회는 실제 행 잠금 목적이므로 결과 변수 사용 여부만 보고 삭제하면 안 됩니다. |
| 4 | R03 / COPY_EQM02 | 이미 CHKPLANEQM.CHKTP='02'로 제한하지만 INSERT에서 MSTCHKKND에 다시 연결해 CHKTP를 가져옵니다. 원본 값으로 대체할 여지는 있으나 현재 INNER JOIN은 마스터가 없는 항목을 제외하는 기능도 합니다. |
| 5 | R03 / LIST_COPY_EQM02 | 한 분기가 원본 설비 목록과 점검항목 두 결과셋을 반환합니다. 팝업 열기는 첫 결과셋, 원본 선택은 두 번째만 사용하므로 각 호출에서 사용하지 않는 조회가 발생합니다. 전체 분기는 사용 중이라 통째로 삭제할 수 없습니다. |
| 6 | R04 / LIST_CYCLE_EQMCD | YEARPLAN을 EQMCD·YEAR로만 연결하고 마지막 GROUP BY FANO로 묶습니다. 실제 PK는 EQMCD·CHKTP·YEAR이므로 구분별 행이 생기면 중복을 가리면서 월별 값 선택이 불명확해집니다. 실제 DB의 같은 설비·년도 복수 행은 현재 0건입니다. |
| 7 | R04 / LIST_CHKPLANEQM_EQM02 및 실적 CRUD 승인 검증 | GRP_REV의 모든 승인 REV를 직접 연결합니다. 승인된 그룹 REV가 여러 개면 연결 행이 늘어납니다. 실제 DB에서 승인 REV가 여러 개인 그룹은 3개입니다. 그룹의 승인 여부를 확인하는 조건 자체는 필요합니다. |
| 8 | R04 / LIST_CHKPLANEQM_EQM02 | PENDREVNUM 조회가 미승인 REV에 LIMIT 1만 사용합니다. 정렬과 현재 승인 REV보다 높은 번호라는 조건이 없어 과거 반려 REV가 안내에 잡힐 가능성이 있습니다. 현재 복수 미승인 REV를 가진 설비는 0건이며 실제 화면 오류가 재현됐다는 뜻은 아닙니다. |

**표 2. 같은 지점의 개선 방향 — 개선 후 제안, 미반영**

| 번호 | 제안하는 개선 방향 | 적용 전 확인할 사항 |
| --- | --- | --- |
| 1 | 두 번째 IF는 PLANTP의 유효성만 검사하고, PLANCD 검증은 첫 IF에서 한 번만 수행합니다. | NULL·빈 값일 때 기존 안내와 중단 동작이 동일한지 비교합니다. |
| 2 | 정규화된 PLANTP의 재검사를 제거하고 PLANCD 미선택 검사만 남깁니다. | 기존 기본값 G 처리와 설비·설비그룹 안내를 유지합니다. |
| 3 | 같은 대상의 잠금 및 상태 집계를 한 번에 수행할 수 있는지 검토합니다. | 선택 행·잠금 범위·동시 승인/반려 및 일괄 승인 결과가 같아야 합니다. 단순 JOIN 삭제 대상은 아닙니다. |
| 4 | CHKTP는 원본 CHKPLANEQM에서 가져오는 방식으로 검토합니다. | 마스터 누락·CHKTP 불일치 데이터와 현재 INNER JOIN의 필터 역할을 먼저 확인합니다. 이 검증 없이 MSTCHKKND JOIN을 삭제하지 않습니다. |
| 5 | 그룹 복사처럼 목록 조회와 상세 조회를 각각 분리해 필요한 결과만 반환합니다. | 두 JavaScript 호출과 store/storeExtend1 연결을 함께 수정·검증해야 합니다. 현재 결과셋을 임의로 삭제하면 상세 조회가 깨집니다. |
| 6 | 정기점검 YEARPLAN 선택 기준을 먼저 확정해 설비당 한 행으로 연결합니다. 이후 외부 GROUP BY 제거 가능성을 검토합니다. | CHKTP='02' 행 없는 과거 데이터의 처리, 월별 값·조회 행수·정렬을 비교합니다. 기존 fallback을 고려하지 않은 조건 추가는 피합니다. |
| 7 | 승인 그룹코드를 PLANCD당 한 행으로 집계해 연결합니다. 설비의 승인 REV 선택 기준은 유지합니다. | 그룹 승인 이력이 여러 개인 경우·그룹 없는 설비·현재 대기/반려 REV가 있는 경우를 비교합니다. 다중 행 WHERE 상관 EXISTS는 사용하지 않습니다. |
| 8 | 현재 승인 REV보다 높은 미승인 REV 중 최신 번호를 명시적으로 선택합니다. | 과거 반려 REV만 있는 경우는 안내를 비우고, 새 대기·반려 REV가 있으면 해당 최신 번호를 표시하는지 검증합니다. |

**유지해야 하는 JOIN**

- R03 설비그룹 조회의 COMTYPE은 그룹명·FM116 정렬·같은 이름 검색에 사용합니다.
- R03 최신 번호 집계와 HEADER 재연결은 각각 최신 번호 선정과 그 REV의 내용 조회 역할을 합니다.
- REV 상세 조회의 HEADER는 PLANTP·PLANCD·REVNUM을 REVCD로 연결합니다. DETAIL에 그 식별정보를 중복 저장하지 않으므로 필요합니다.
- 작성자와 승인자의 MSTEMP JOIN은 서로 다른 사람의 이름을 가져옵니다.
- R04 실적 집계의 RST_REV는 각 월에 실제 적용했던 REV 번호를 표시합니다.

**검증 결과**

격리 MariaDB 10.2.44에서 원본 R04와 정리한 R04를 함께 컴파일했습니다. 19개 검증이 통과했습니다. 모든 분기의 호출 존재, 조회 행·정렬·적용 REV·점검자, 실적 등록·수정·삭제 결과, 필수값·중복·승인·미사용 설비·미계획 월 검증을 비교했습니다. 이전 실적의 적용 REV 보존과 파라미터 재등록 범위·재실행·호출 순서도 확인했습니다. 미사용 CHKCYCLE 반환 컬럼을 제외한 비교 결과는 동일했습니다.

JavaScript 구문 검사를 통과했습니다. 실제 브라우저 E2E와 SQL 성능 벤치마크는 이번 검증에 포함하지 않았습니다. 개선 후보의 성능 향상은 확정하지 않았습니다.
