# EQM1001 정기점검 REV 독립 관리 최종안

작성일: 2026-10-08. 최신 로컬 R03·R04·R05 및 전환 SQL 기준이며 실제 서버 반영 여부와 구분한다.

## 적용 기준

그룹 계획과 설비 계획은 각각 자기 REV와 점검항목을 관리한다. 설비 계획을 변경해도 소속 그룹의 REV·항목·승인상태는 변경되지 않는다. 그룹 계획을 변경해도 설비별 계획에는 복사하거나 승인하는 작업이 발생하지 않는다.

REV DETAIL의 항목별 사용여부는 관리하지 않는다. 해당 REV의 DETAIL에 항목이 있으면 그 계획에 포함되고, 없으면 제외된다. 이후 REV에서 다시 추가할 수 있다.

R04는 그룹과 설비의 최신 승인본을 각각 찾고 두 항목 목록을 UNION ALL로 보여준다. 화면의 적용 REV는 REV.0 형식으로 표시한다. 점검실적에는 두 적용 REV 키와 각 항목의 출처를 기록한다.

## 테이블별 역할과 최종 연결

### MSTEQMREV_HEADER: 누구의 어떤 REV인지 관리

- REVCD: REV 한 건의 고유키. GETKEY('REVCD')로 생성한다.
- PLANTP: G는 그룹 계획, E는 설비 계획이다.
- PLANCD: G이면 설비그룹코드 EQMGUBUN, E이면 설비코드 FANO이다.
- REVNUM: 대상별 번호이며 최초 REV.0부터 시작한다.
- APRVSTT: 빈 값은 대기, A는 승인, R은 반려이다. REV 자체가 없으면 화면의 승인상태도 공란이다.
- REMARK: 개정내용이다. REQTIME·REQEMP·REQPRG는 저장·재요청 정보, APRVTIME·APRVEMP·APRVPRG·REJREASON은 현재 처리 상태와 사유이다.
- PK는 REVCD, 대상별 REV 번호의 유일 기준은 PLANTP·PLANCD·REVNUM이다.

### MSTEQMREV_DETAIL: 해당 REV에 포함된 점검항목

- PK는 REVCD·CHKKNDCD이다. REVCD로 HEADER 한 건에 연결한다.
- 점검명·점검항목·방법·값구분·주기·정렬순서·비고와 등록·수정 정보를 저장한다.
- USEYN은 제거한다. HEADER에 있는 PLANTP·PLANCD·REVNUM·EQMCD도 DETAIL에 반복 저장하지 않는다.
- 같은 점검코드가 이전 REV에 있어도 현재 수정 중인 REV에 없다면 다시 추가할 수 있다.
- 저장은 정렬순서·비고를 변경한다. 삭제는 수정 대상 REV에서 항목 행을 제거한다.
- 승인된 REV의 기존 항목은 보존한다. 최신 승인본에서 추가·삭제·수정을 진행하면 해당 대상의 다음 REV를 만든 뒤 변경한다. 이전 REV는 조회 전용이다.

MSTEQM.USEYN은 설비 사용여부, COMTYPE.USEYN은 그룹 코드 사용여부, MSTCHKKND.USEYN은 점검항목 기준정보의 사용여부이므로 유지한다. 제거 대상은 REV DETAIL의 사용여부뿐이다.

### CHKPLANEQM_APRV: 승인·반려 처리 기록

- PK는 GETKEY('APRVKEY')로 생성하는 APRVKEY이다.
- REVCD는 처리한 HEADER를 가리킨다.
- 승인·반려의 상태, 처리자, 시간, 반려사유를 건별로 기록한다.
- HEADER는 해당 REV의 현재 상태를 보여주고, 이 테이블은 처리 기록 팝업에 사용한다.
- 그룹 승인·반려는 해당 그룹 REV만 처리하며 설비별 REV 상태를 함께 변경하지 않는다.

### CHKRSTEQM: 점검실적 전체 정보

- CHKRSTKEY는 점검실적 한 건의 고유키이다.
- EQMCD·BASEDATE·EMPCD는 점검한 설비·날짜·점검자이다.
- 기존 REVCD는 당시 적용한 설비 계획의 HEADER 키를 저장한다.
- 추가 GRPREVCD는 당시 적용한 그룹 계획의 HEADER 키를 저장한다.
- 두 컬럼에는 화면 문자열이나 REVNUM을 저장하지 않고 HEADER의 고유키 REVCD를 저장한다.
- 어느 한쪽 계획만 사용한 점검이면 해당 키만 저장하고 다른 키는 빈 값이다.

### CHKRSTEQMKND: 점검실적의 항목별 결과

- CHKRSTKEY로 점검실적 전체 정보에 연결한다.
- PLANTP는 해당 행의 출처이며 G는 그룹, E는 설비이다. 구 실적의 빈 값은 유지한다.
- CHKKNDCD·점검명·방법·값구분은 당시 항목 정보이고 CHKVALUE는 입력한 점검값이다.
- PK는 CHKRSTKEY·PLANTP·CHKKNDCD이다. 같은 점검코드라도 G와 E는 별도 행이다.
- 개별 항목에 REV 키를 다시 저장하지 않는다. PLANTP가 G이면 실적의 GRPREVCD, E이면 REVCD로 적용 REV를 찾는다.
- 같은 출처의 동일 점검코드는 중복 저장할 수 없다.

### 기존 테이블

- CHKPLANEQM: 테이블과 기존 데이터는 유지하지만 R02~R05의 정기점검 업무에서는 참조하거나 저장하지 않는다.
- CHKPLANEQM_YEARPLAN: 설비별 월 점검자·주기계획에 계속 사용한다. R03 주기 조회는 사용 중인 모든 설비가 대상이며 저장 시 승인 계획 존재 검사를 하지 않는다.
- MSTCHKKND: 정기점검 항목 기준정보다. 추가 목록은 CHKTP='02', USEYN='Y' 중 해당 최신 REV에 아직 없는 항목을 조회한다.

## CNC 예시로 보는 업무 흐름

설비그룹코드 FM116I210N(CNC), 설비코드 I2C-003N을 설명용 예시로 사용한다.

1. 그룹 탭에서 004·005 항목을 추가한다. 그룹 HEADER에 REV.0이 생기고 그 REVCD의 DETAIL에 두 항목이 들어간다. 설비 HEADER는 생성되지 않는다.
2. 설비 탭에서 004·998 항목을 추가한다. 해당 설비의 REV.0과 두 DETAIL이 생성된다. 그룹 REV.0과 그 항목은 그대로이다.
3. 각각 개정내용을 저장하고 승인한다. 각 HEADER는 A가 되고 각 승인 기록이 생성된다. DETAIL은 그대로 유지된다.
4. 설비에 006을 추가한다. 설비 REV.1에 이전 항목을 복사하고 006을 추가한다. 그룹 REV는 여전히 0이다. 설비 REV.1이 대기 중이면 R04는 이전 설비 승인본 REV.0을 사용한다.
5. 그룹에서 005를 삭제한다. 그룹 REV.1을 만들고 005를 제거한다. 그룹 REV.0의 005는 보존되며 설비 REV.1에는 영향이 없다.
6. 그룹 REV.1과 설비 REV.1을 승인한다. R04 팝업은 그룹의 004와 설비의 004·998·006을 네 행으로 보여준다. 그룹 행에는 REV.1, 설비 행에도 REV.1만 표시되며 내부 출처는 다르다.
7. 점검실적을 저장한다. CHKRSTEQM에는 두 REV.1의 서로 다른 고유키를 기록하고, CHKRSTEQMKND에는 G/004, E/004, E/998, E/006의 결과를 각각 저장한다.
8. 이후 그룹 REV.2에서 005를 다시 추가할 수 있다. 승인 후 새 점검에 적용한다. 앞서 저장한 실적을 수정 조회하면 당시 적용한 그룹·설비 REV.1과 저장된 네 항목을 유지한다.

반려 후에는 보완하고 개정내용 저장·재요청을 거친 뒤 승인한다. 현재 수정 대상만 다시 대기가 되고, 그룹과 설비 사이에 상태 전파는 없다. R04에서는 대기·반려본을 실행하지 않고 각 대상의 최신 승인본을 사용한다.

기존 테이블을 유지하고 정기점검 데이터를 비운 DB가 기준이다. 기존 데이터 이전·이력 복원·실적 출처 보정·재삭제는 필요 없다. 아래 구조 파일은 테이블마다 ALTER TABLE 한 문장으로 분리되어 있다. SQL은 로컬 파일이며 실제 DB 반영은 사용자가 진행한다.

프로시저는 DBeaver의 해당 프로시저 소스 편집기에 전체 내용을 붙여 넣고 저장한다. 내부 세미콜론 때문에 프로시저 SQL에서 Ctrl+Enter로 일부 문장만 실행하면 안 된다. 파라미터 파일은 해당 페이지 하나의 등록만 처리하며 START TRANSACTION부터 COMMIT까지 파일 전체를 실행한다. 다른 페이지나 테이블 변경이 섞여 있지 않다.

MSTEQMREV_HEADER는 이번 변경에서 ALTER가 필요 없다. REVCD PK와 UNIQUE(PLANTP,PLANCD,REVNUM)은 조회 파일로 확인한다. 실제 구조가 이 기준과 다르면 해당 차이를 먼저 확인한다. CHKPLANEQM과 기준정보는 변경하지 않는다.

예전 일괄 PLAN_REV_DEPLOY.sql과 다중 테이블 전환 PLAN_REV_INDEPENDENT.sql은 삭제했다. PLAN_REV_INIT·PLAN_REV_REVCD·PLAN_APRV_HISTORY·PLAN_REV_NORMALIZE·PLAN_REV_RESET은 이번 초기화된 DB의 실행 목록에 포함하지 않는다. 필요한 구조 변경은 위 네 ALTER 파일에 담겨 있다. SQL에 기존 데이터 이전·승인이력 보충·발번·업무 데이터 삭제·백업 테이블 생성은 없다.

업무 데이터가 비어 있어도 프로시저 호출용 SYSTEM_PARAMETERS는 새 입력값 정의에 맞춰 등록해야 한다. 이는 점검 데이터 이전이 아니다. R03에서 USEYN_LIST를 제거했으므로 30개가 아니라 29개여야 한다. 한 단계씩 성공과 결과를 확인한 후 다음 단계로 진행한다.

## 적용 후 확인할 결과

- DETAIL에 USEYN·PLANTP·PLANCD·REVNUM·EQMCD가 없다.
- HEADER에는 대상 구분·코드·REV 번호가 있고 DETAIL은 REVCD로 연결한다.
- CHKRSTEQM에는 REVCD와 GRPREVCD가 있다.
- CHKRSTEQMKND에는 PLANTP가 있고 PK 순서는 CHKRSTKEY·PLANTP·CHKKNDCD이다.
- SYSTEM_PARAMETERS: R02 21개, R03 29개, R04 15개, R05 10개다. R03에서 USEYN_LIST 한 개를 제거했다.
- R03 두 탭 및 그룹 복사 팝업에 항목 사용여부 컬럼이 없다. 선택 행 체크박스는 CRUD 선택에 계속 사용한다.
- 조회·추가·저장·삭제·복사·REV 조회·승인·반려·출력 모두 DETAIL의 USEYN을 참조하지 않는다.
- R04는 최신 승인 그룹 항목과 최신 승인 설비 항목을 UNION ALL로 반환하며 같은 코드를 각각 저장한다.

## 검증 결과와 범위

실서버와 연결되지 않은 네트워크 none MariaDB 10.2.44에서 R02~R05 프로시저 4개 컴파일, 계획·실적 시나리오 38건을 검증했다. JavaScript 화면 이벤트 모의검증 17건을 포함하여 기능 검증 총 55건이 통과했다.

- 두 탭의 등록·저장·삭제·복사·재추가, 개정내용 저장·승인·반려 후 보완·재요청, 다른 대상의 REV 무변경, 이전 승인본 보존 및 변경 없는 저장의 불필요한 REV 생성 방지를 확인했다.
- 각 대상에서 REV.3의 항목을 REV.4에서 삭제한 뒤 REV.5에서 다시 추가할 수 있고, 이전 REV의 항목과 다른 대상의 REV는 보존되는 것을 확인했다.
- 최신 승인 그룹·설비 항목의 UNION ALL, 동일 점검코드 두 건의 등록·수정, 적용한 두 REV 키 보존, 오류 입력·중복 월 등록·누락/중복 항목의 롤백을 확인했다.
- 기존 실적의 REV 연결 초기화 후 조회·수정·삭제, 기존 CHKPLANEQM 데이터 무변경, 주기관리 승인 검사 미적용을 확인했다.
- 이전 검증에서는 빈 DETAIL 전환과 기존 데이터가 있는 경우의 전환 차단을 확인했다. 이번 실행 파일은 초기화 확인 SELECT와 테이블별 ALTER로 분리했다.
- 이전 일괄 SQL의 검증 결과는 유지한다. 현재 실행 방식은 개별 ALTER와 페이지별 프로시저·파라미터 등록이다. 아래에 분리 실행 검증을 별도로 기록한다.
- 변경 JS 문법, 소스/문서의 UTF-8 BOM·CRLF, 검사한 원본과 최종 반영 파일의 일치를 확인했다.

실제 서버 DB DDL/DML·파일 배포·실제 브라우저 CRUD·PDF 출력은 수행하지 않았다. 이번 턴에는 실제 DB의 최신 컬럼·데이터를 재조회하지 않았으며, 격리 DB는 이전에 확보한 실제 스키마 기반 검증용 구성이다. C# 소스와 보고서 양식의 변경은 없다.

이번 분리 실행 방식은 격리 DB에서 추가 검증 16건이 통과했다. 네 ALTER 파일의 순차 적용·반복 실행, APRVID 자동증가 PK에서 APRVKEY로 변경, 네 페이지 프로시저 개별 컴파일, 페이지별 파라미터 재등록·오래된 순번 제거·다른 페이지 보존, 변경 전후 SELECT와 BOM·CRLF를 확인했다. 구조 파일에는 테이블마다 ALTER 한 문장만 있으며 데이터 이전·업무 데이터 변경·키 발번은 없다. 이번 작업은 실행 SQL과 안내 문서 정리이며 업무 프로시저 및 화면 동작은 변경하지 않았다. 실제 DB에는 적용하지 않았다.
